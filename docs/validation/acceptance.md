# Приёмка лабораторного MVP: issue #1–5

Дата: 7 ноября 2026 года (проверки начаты 6 ноября). Приёмка после аудита реализации и сохранённых артефактов.
Проверки и исправление подготовлены в ветке `test/mvp-issues-1-5-acceptance`
от `network-control-platform`; основной объём работ экосистемы сюда не включён.

## Что добавлено для #1

`tests/lab/test_scenario_effects.py` проверяет реальные пакеты в root Linux,
а не только корректность конфигов. Каждый случай выполняется трижды:

| Случай | Проверяемый наблюдаемый результат |
| --- | --- |
| Потери A | При заданных 50% потерь измеренная доля между 25% и 75% на ≥200 отправках; B теряет <5% |
| Обрыв и восстановление A | Реальные down/up, окно без ответов >1 с, ответы до и после; B без аналогичного разрыва |
| Перестановка A | В capture получателя >10 инверсий sequence, B без инверсий; на каждой ветви >200 пакетов |
| Плохой обратный путь A | Медиана RTT A больше B минимум на 75 мс; B остаётся <40 мс |
| Перегрузка A | Живой UDP-фон, backlog и drops на A, рост p95 RTT A, здоровая B |
| Общая перегрузка | UDP-фон, backlog и drops на общем узле C, рост p95 RTT обеих ветвей |

Первый Linux-прогон выявил дефект восстановления: административный `down`
удалял статический обратный маршрут на ветви. `up` восстанавливал интерфейс,
но не маршрут к loopback-адресу отправителя. Теперь `Topology.set_path_state()`
после `up` явно восстанавливает обратный маршрут. Проверка требует реальных
ответов до и после окна отказа, а не только успешного вызова `ip link set`.

До внесения netem разрешаются соседи обеих ветвей: ARP не включается в оценку
потерь ICMP. При link down ping может не увеличивать sequence при sendmsg error,
поэтому проверяется временной разрыв ответов и их восстановление. Для перегрузки
используется p95 вместе с backlog/drops и подтверждённым фоном: медиана только
успешных ответов при потерях может быть смещена к периоду после нагрузки.

В каждом запуске проверяются завершение, целостность manifest/files и отсутствие
оставшихся namespaces. Численные границы — критерии этого стенда с заданными
параметрами, не характеристики МКС и не точные оценки вероятности потерь.
Три повтора — функциональная приёмка; длительная статистическая оценка остаётся #7.

## Что добавлено для #5

`tests/selection/test_diagnostics.py` содержит 14 проверок:
локальная очередь отправителя; отдельные A/B с ожиданием sender queue, KMS,
receiver queue/processing/key; отсутствие свидетельств; неоднозначная общая
деградация с известным и неизвестным общим участком. Для каждого path-specific
свидетельства проверяются scope, альтернативы и исчезновение после устаревания.

Найден и исправлен дефект: старое наблюдение sender queue или ожидания ключа
могло оставаться основанием диагноза. Теперь snapshot передаёт возраст наблюдения
очереди, diagnose применяет настроенный max_age_ms к очереди/KMS/receiver и
показывает возраст компонентных свидетельств. После устаревания доступных
оснований вывод — insufficient_evidence / not_established. Истинные причины
из truth не используются. Общий высокий RTT остаётся гипотезой, не доказанной причиной.

## Область готовности #2–4

Подтверждаются тестами KMS, commands, telemetry_lab, collection и incidents:
согласованные тестовые ключи и shared/separate pools, очередь/TTL/refill/отказы,
AEAD и привязка ACK, bounded queues, dedup/restart, startup/steady/rotation,
возникновение/доступность событий, разделение truth, manifest/хеши и отложенные
эпизоды. Обязательное ожидание ключа включено в дедлайн команды.

Для #4 «отложить final» выполнено; «провести длительный независимый final» —
задача #7. В Linux собираются накопленные tc/ip/CPU/RSS, а не готовая экосистема
аналитики нагрузки. Макет KMS доверенный лабораторный, физическая QKD не моделируется;
deadline получателя предполагает один monotonic clock domain. Реальные туннели,
операторские API и произвольные физические хосты требуют отдельной приёмки.

## Воспроизведение и доказательства

Локальная регрессия:

```bash
.venv/bin/python -m pytest -q
.venv/bin/ruff check .
.venv/bin/ruff format --check .
```

Root Linux после установки iproute2/iputils-ping/iperf3/tcpdump/pytest/cryptography:

```bash
sudo modprobe sch_netem
sudo modprobe sch_fq_codel
sudo env PYTHONPATH=src python3 -m pytest -q \
  tests/lab tests/selection tests/kms tests/commands tests/telemetry_lab \
  --basetemp=/tmp/ql-acceptance --junitxml=/tmp/ql-acceptance-results.xml
```

Workflow `Linux packet lab` сохраняет JUnit, исходники опыта, scenario, manifest,
журналы, queue snapshots и PCAP как артефакт `packet-lab-acceptance` на 14 дней.
Служебный TCP API KMS исключён из сетевого capture.

## Уточнения прежних функциональных проверок

Проверка выбора реальной ветви B теперь явно прогревает измерения и отключает
стартовое удержание в этом сценарии. Сами hold/hysteresis/emergency по-прежнему
проверяются отдельным policy-тестом. Ранее корректное первое решение `A / hold`
противоречило требованию теста «никакого пакета A» даже при известных RTT.

В проверке hedging подтверждаются первый ACK от B, своевременность относительно
заданного дедлайна 500 мс, лимит копий, отмена и одно исполнение. Прежнее
абсолютное требование <100 мс было нестабильным на общем CI-runner и смешивало
функциональную приёмку с производительностью. Порог эксплуатационного SLO не
изменён и не объявляется достигнутым: его независимая оценка остаётся в #7.

# Политики на постепенных изменениях

## Запуск

```bash
uv run python -m quantum_link_optimizer.experiments.routing.run \
  --plan lab/experiments/routing.json --output artifacts/experiments/routing-01
```

Семь сценариев × seeds 5001/5003 × семь политик, 22 команды при 13,3/с, восемь в полёте
`ramp-a` поднимает задержку A с 30 до 80 мс в одну сторону за эпизод,
`periodic-a` качает её 20–80 мс с периодом восемь команд

## Политики

| Политика | Что делает |
| --- | --- |
| `ewma-before` | EWMA без перезапуска и без заранее запрошенного ключа |
| `last` | Последний RTT пробы |
| `ewma` | EWMA заново после ступени, ключ заранее |
| `ewma-copies` | Копия через 40 мс |
| `ewma-risk-copies` | Копия после p90 RTT основного пути, если медленных проб от 10% |

## Выводы

- Перезапуск EWMA после ступени помог в swap и ramp-a на две команды,
  но в periodic-a детектор ловит каждое колебание и EWMA гоняется за ним, 5 против 10,
  в сумме эффекта нет, поэтому `ewma_restart` выключен по умолчанию
- Копии по риску сохранили большую часть выигрыша копий при байтах в 6,3 раза меньше
- В ramp-a и periodic-a постоянный B лучше любой адаптивной политики:
  реакция по прошлым пробам отстаёт от изменения, здесь у прогноза есть запас
- `last` реагирует быстрее EWMA и в этих сценариях выигрывает 7 команд
- slow-kms остаётся 0 даже с ключом заранее и неблокирующим получателем:
  KMS с задержкой 60 мс на запрос насыщен выдачей, получением ключа получателем
  и опросом запаса каждые 100 мс, сам опрос занимает около 60% его времени

Оценка «сетевого потолка» по пробам показала 44/44 во всех сценариях,
она не учитывает ключи и очередь и годится только как верхняя граница

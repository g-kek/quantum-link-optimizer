# Несколько команд в полёте

## Что изменилось

Router и Sender ждали ACK команды перед отправкой следующей
При RTT больше интервала между командами очередь росла без предела:
в normal/fixed B задержки шли 97 → 118 → 138 → … → 589 мс при RTT пути около 90 мс

Теперь в полёте до `max_in_flight` команд, по умолчанию 8
Смену ключа в сессии выполняет одна команда, остальные ждут её под блокировкой
ACK сопоставляется по ID команды и ключу, порядок `set` по-прежнему проверяет получатель
`coalesce=True` отменяет старые `set` в очереди, если пришёл более новый

Pacing в опытах был 5 команд/с при нагрузке 10–13,3/с, теперь 20/с
Команда, которой пришлось бы ждать pacing дольше 20 мс, получает отказ сразу

## Доставка

ACK ≤100 мс из 352 поступлений на политику

| Политика | Одна команда | Восемь команд | Неизвестные исходы |
| --- | ---: | ---: | ---: |
| Fixed A | 101 | 151 | 104 → 74 |
| Fixed B | 24 | 127 | 114 → 68 |
| EWMA | 126 | **167** | 104 → 64 |
| Прогноз | 128 | 167 | 108 → 64 |
| EWMA + копии | 136 | 166 | 101 → 69 |
| EWMA + pacing | 127 | 167 | 106 → 64 |

По сценариям для EWMA

| Сценарий | Одна команда | Восемь команд | Что ограничивает |
| --- | ---: | ---: | --- |
| normal | 44 | 44 | — |
| swap | 27 | 38 | Реакция на смену быстрого пути |
| common-700 | 0 | 0 | Оба пути 700 мс |
| slow-kms | 0 | 0 | Ключ ждут и отправитель, и получатель |
| key-exhaustion | 6 | 6 | Три ключа без пополнения на seed |
| shared-queue | 0 | 0 | Общий участок 20 кбит/с |
| receiver-restart | 44 | 44 | — |
| loss-a | 5 | 35 | Потери 25% на A |

Копии и прогноз больше не добавляют своевременных команд, копии стоят 77 000 байт
Оставшиеся нули — физические ограничения сценариев, выбор пути их не снимает
В slow-kms хвост — ожидание ключа у отправителя и у получателя,
очередь получателя растёт, пока он ждёт ключ

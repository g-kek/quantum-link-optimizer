# Польза прогноза для доставки команд — issue #6

7 ноября 2026. Лабораторные UDP-команды с AEAD, TCP KMS и программными
задержками. Это не измерения МКС и не физическая модель QKD.

## Протокол

```bash
uv sync --locked --extra lab
uv run python -m quantum_link_optimizer.experiments.forecasting.run \
  --plan lab/experiments/forecast-benefit.json \
  --output artifacts/experiments/forecast-benefit-01
```

Выходной каталог должен быть новым. 20 train-эпизодов (seeds 11/23),
10 validation-эпизодов (seed 101), 720/360 строк кандидатов A/B.
Для команды размечен только фактически выбранный путь: 360/180 train/validation
меток опоздания. Пары A/B и строки одного эпизода не независимы.
Seeds 1009/1013 зарезервированы для отдельной приёмки #7.

Пять условий: норма, смена быстрой ветви, оба RTT 700 мс, медленный KMS и
исчерпание ключей. Скрытые case/seed/fault ID, будущие исходы и truth не входят
в признаки. Запас ключей поступает через настоящий ответ API `state`, с возрастом
и проверкой доступности. Polling использует очередь KMS и влияет на опыт одинаково
для всех политик. Значение refill — объявленный параметр макета, не датчик физической QKD.

MLP: 15 числовых признаков + 15 индикаторов отсутствия, слой 12 ReLU, два logits.
Медианы/mean/scale вычисляются только по train; 80 фиксированных эпох Adam,
lr=0.01, seed=42. Модель офлайн, JSON-веса загружаются один раз перед опытом.
Вероятности: (1) команда не получает ACK исполнения за 100 мс, включая отказы;
(2) доступный пул будет пуст в момент t+250 мс. Для второй головы последние
наблюдения без известного будущего не размечаются. Это состояние на горизонте,
а не вероятность любого кратковременного исчерпания внутри окна.

Простые ориентиры: EWMA RTT и баланс `available / (demand - refill)` при
положительном расходе. Отсутствие данных и отсутствие положительного drain
различаются; нулевой запас означает нулевое время до исчерпания.

## Живые сравнения

Validation содержит 50 отдельных запусков: fixed A/B и полный факторный набор
forecast/EWMA × копии вкл/выкл × pacing вкл/выкл. На политику — 90 команд;
все поступления входят в знаменатель. Настройки hold/margin и лимитов одинаковы,
hedge=40 мс, pacing=5/с против входных 10/с. Нельзя удалять ожидание pacing из задержки.

| Политика | ACK ≤100 мс / поступило |
| --- | --- |
| EWMA | 35 / 90 |
| Прогноз без копий/pacing | 35 / 90 |
| EWMA + копии | 38 / 90 |
| Прогноз + копии | 37 / 90 |
| Варианты с pacing | 3 / 90 |

Для обоих путей 700 мс и для медленного KMS получено 0/18 вовремя у каждой
политики. Выбор не создаёт быстрый путь и не устраняет очередь выдачи ключа.

Offline Brier модели: опоздание 0.0631 против train-frequency 0.1902;
пустой пул 0.000034 против 0.1600. У правил Brier 0.4663 и 0.0222 соответственно;
coverage правила RTT 178/180, модель 180/180 — знаменатели явно различаются.
Эти числа описывают этот небольшой набор, а не калибровку для реальной сети.

## Решение

В этом запуске лучший прогноз меток не дал прироста своевременных команд
поверх EWMA. **Прогноз не рекомендуется включать по умолчанию.** Эффект копий
и отрицательный эффект выбранного pacing показаны отдельно, не приписаны ML.
Положительный validation-результат сам по себе также не был бы основанием для внедрения.

Независимые final-эпизоды и измерение overhead выполняются отдельно в #7
после фиксации модели, политик и preprocessing. Объём и длительность этих опытов
не заменяют длительный план 64 часа и операторский пилот.

[Численные результаты и хеши](../evidence/forecast-benefit.json).
Полные данные, JSON-веса, source snapshots, события и manifest находятся в
`artifacts/experiments/forecast-benefit-01/` и не коммитятся как обучающие результаты.
Проверки: `uv run pytest -q tests/experiments/forecasting tests/selection`.

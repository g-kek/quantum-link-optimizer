## Общая оценка

У проекта есть рабочая основа для воспроизводимых офлайн-экспериментов:
хронологическое разбиение, нормализация только по train, удаление пересекающих
границы многогоризонтных целей, сравнение с простыми алгоритмами и сохранение
моделей. Отдельно проверяется, что replay принимает решение до чтения исхода
и совпадает с пакетной оценкой на каждом тестовом шаге.

Главный следующий вопрос — в каких условиях прогноз приносит пользу выбору
канала. Сейчас такой пользы не показано. Увеличение нейросети само по себе
не следует из результатов: сначала нужны сопоставимые ограничения алгоритмов,
разбор ошибок и более разнообразные измерения.

## Воспроизведённые проблемы

Все три пункта имеют приоритет P2: обычные синтетические запуски проходят,
но эти случаи нужно закрыть перед работой с внешними данными.

### 1. Atlas теряет успешные измерения после тайм-аута в общих метриках

Место: [atlas.py, строки 64–68 и 103–104](../src/quantum_link_optimizer/atlas.py#L64).
Маска требует одновременно известные текущий и предыдущий RTT. Это правильно
для ошибки persistence, но та же маска применяется к `test_breaches`,
`no_test_events`, среднему и p95 тестового RTT.

Воспроизведение: JSON из 20 записей одного measurement/probe/destination,
обычный RTT 7 мс; в строке 16 timeout, в строке 17 RTT 150 мс. Последние четыре
строки образуют тест. Получается:

| Показатель | Текущий отчёт | Все доступные текущие RTT теста |
| --- | ---: | ---: |
| Измерения с RTT | 2 в `evaluated_origins` | 3 |
| Превышения 100 мс | 0 | 1 |
| Средний RTT, мс | 7.0 | 54.667 |

Сейчас `no_test_events=true`, хотя в тестовом файле есть событие. Ограничение
парной оценки описано в протоколе, но имена общих полей легко прочитать как
характеристики всего доступного теста.

Исправление: отдельная маска текущих доступных RTT для описания теста и маска
пар для persistence. Сохранять оба знаменателя и число исключений из-за
неизвестного предыдущего RTT. Добавить регрессионный тест с превышением сразу
после timeout; тайм-ауты учитывать отдельно, без выдуманного числового RTT.

### 2. Нечисловой прогноз прерывает replay вместо записи отказа

Место: [shadow.py, строки 52–56](../src/quantum_link_optimizer/shadow.py#L52)
и [сериализация журнала](../src/quantum_link_optimizer/shadow.py#L80).
`RiskSelector.step` возвращает `abstain_invalid_prediction` для NaN/Inf,
но `decide` всё равно возвращает исходные массивы прогнозов в журнал.
`json.dumps(..., allow_nan=False)` выбрасывает `ValueError` до записи решения.

Воспроизведение: создать `WarningForecaster(4, (1, 5))`, присвоить последнему
слою NaN в bias и передать в `replay_stream` обычную синтетическую историю.
Результат: `ValueError: Out of range float values are not JSON compliant: nan`.
Это отдельная проверка повреждённого прогноза; штатные веса NaN не дали.

Исправление: проверить конечность всех горизонтов и RTT перед сериализацией;
при отказе записывать `null` вместо невалидных прогнозов и сохранять причину.
Проверить checkpoint при загрузке: схему, scaler, положительные масштабы,
наличие горизонта 1 и конечность весов. Тест должен подтвердить, что решение
с отказом записано до чтения текущего исхода и журнал остаётся валидным JSONL.

### 3. Проверка формы CSV-строк неполная

Места: [observations.py](../src/quantum_link_optimizer/observations.py#L30)
и [telemetry.py](../src/quantum_link_optimizer/telemetry.py#L63).
Порядок колонок заголовка проверяется, количество значений каждой строки — нет.

Подтверждены два случая:

- Внешняя строка без последнего поля `provenance` при корректном заголовке
  вызывает `AttributeError: 'NoneType' object has no attribute 'strip'`.
  CLI перехватывает только `ValueError`, поэтому пользователь получает traceback.
- Добавление `,unexpected-extra-field` к строке корректного синтетического CSV
  принимается без ошибки: `csv.DictReader` кладёт лишнее значение под ключ `None`.

Исправление: проверять лишние и отсутствующие значения до преобразования типов,
сообщать номер строки и имя поля через `ValueError`. Добавить тесты короткой
и длинной строки для обеих схем. Проверку malformed JSON Atlas и ошибки
открытия файлов также стоит оформить понятными сообщениями CLI.

## Что подтвердили запуски

Окружение: macOS arm64, Python 3.12.0, NumPy 2.5.4, PyTorch 2.14.1,
зависимости установлены через `uv sync --locked --python 3.12`.

- `pytest -q`: 37 тестов прошли.
- `ruff check .`: замечаний нет.
- `ruff format --check .`: все 25 Python-файлов уже отформатированы.
- `experiment`: настройки по умолчанию, 4000 измерений, seed 42, до 60 эпох.
- `benchmark-suite`: seeds 41/42/43, normal и shared-stress, по 4000 измерений,
  40 эпох. Во всех шести запусках replay совпал с пакетными решениями,
  coverage = 1, abstentions = 0.

Это проверки текущего синтетического контура. Настоящий двухканальный набор
и исходный файл Atlas в Git не поставляются; Atlas проверен на искусственно
составленных входных записях, включая сценарий ошибки выше.

## Что делать дальше

### 1. Закрыть ошибки данных и журнала

Исправить три случая выше отдельными небольшими изменениями с регрессионными
тестами. Для модели добавить версию формата checkpoint и проверку обязательных
полей. Сохранить строгую JSON-сериализацию и причинность replay.

Готово, когда повреждённые данные отклоняются с понятной причиной, нечисловой
прогноз даёт записанный отказ, а событие после timeout не исчезает из сводки Atlas.

### 2. Выяснить, почему селектор проигрывает

Сейчас risk-selector ограничен `min_hold_samples=5` и гистерезисом 3 мс,
а previous-RTT учитывает только стоимость переключения. Сравнение корректно
описывает готовые политики, но смешивает эффект прогноза, риска и удержания.

Добавить сравнения при одинаковых ограничениях: previous-RTT с тем же hold
и гистерезисом, прогноз RTT с нулевым штрафом риска, полный risk-selector.
Отдельно отключать hold, гистерезис и штраф риска. Все настройки выбирать
по train/validation и проверять на новом тестовом периоде.

Выводить реализованную стоимость `RTT + penalty * breach + switch_cost`,
совместно со средним, p95, SLA и числом переключений. По журналам разбирать
эпизоды запоздалого переключения, ошибочного прогноза и одновременного
ухудшения обоих каналов. Это покажет, какой компонент нужно менять.

Готово, когда можно объяснить проигрыш на уровне эпизодов и отделить качество
прогноза от ограничений селектора. Победа нейросети не является условием готовности.

### 3. Сделать benchmark разнообразнее и оценить неопределённость

Оба сценария используют один генератор; `shared-stress` добавляет 25 мс
ко всему ряду до разбиения. Это не проверка внезапного изменения условий
после обучения. Seed одновременно задаёт телеметрию и инициализацию модели.

Разделить seed данных и модели; добавить сдвиг только после обучения,
изменения частоты и длительности нагрузки, пропуски, тайм-ауты и нерегулярные
интервалы. Разрешённые действия при неполной истории описать заранее.
Использовать несколько временных train/validation/test-разбиений с тем же
purge, а различия политик оценивать парно на одинаковых рядах. Для оценки
неопределённости учитывать временную зависимость наблюдений, а не считать
каждую секунду независимым экспериментом.

Для вероятностей добавить проверку калибровки и согласованности вложенных
горизонтов; калибратор обучать на отдельном участке до финального теста.
Сначала сравнить с простыми сглаживанием и линейным прогнозом.

Готово, когда преимущество или отсутствие преимущества описано по сценариям,
с разбросом результатов и заранее выбранным критерием полезности.

### 4. Подготовить реальные измерения двух каналов

Собирать синхронные RTT обоих путей с UTC, точками измерения, частотой проб,
порогом timeout и происхождением данных. Сохранять потери и разрывы.
Измерить реальную стоимость переключения. Отдельно собирать QKD/PTP-показатели,
если задача требует проверять связь с ними.

До переноса модели согласовать интервал измерений: разрешение большого
`max_gap_seconds` не делает секундную модель пригодной к редким измерениям.
Начать с офлайн-базовых алгоритмов, затем переобучения на реальной истории
и shadow-проверки на новом периоде. Требования — в [обзоре данных](data-sources.md).

Готово, когда есть независимый тестовый период целевой пары каналов,
понятные знаменатели и согласованный критерий перехода к следующему этапу.

### 5. Упростить сопровождение и выпуск

Согласованно перенести готовые этапы в `main`: сейчас обычный clone получает
только описание. Для заявленной поддержки Python 3.12/3.13 расширить CI
на обе версии. Дополнить warning/risk/suite-отчёты версиями Python и библиотек,
commit SHA, параметрами обучения и схемы артефактов. Базовый `experiment`
часть этих данных уже сохраняет.

По мере роста кода вынести запись артефактов в общий модуль: сейчас risk,
shadow, atlas и suite импортируют `dump_json` из модуля обучения warning.
Добавить типы публичным функциям и общий объект параметров эксперимента.
Для больших рядов заменить материализацию всех окон и CSV в памяти на
пакетную обработку; текущий размер 4000 строк этого ещё не требует.

Готово, когда новый участник может клонировать `main`, воспроизвести пример
и по отчёту понять, какой код, данные и настройки его создали.
